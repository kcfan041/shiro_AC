# Area Commander（shiro_AC）設計文件

> 狀態：草案 v0.1（MVP 前）
> 本文件記錄目前的構想、已決定事項與待定問題，會隨開發持續更新。

---

## 1. 核心概念

**Area Commander** 是以 Discord 為介面的戰爭指揮遊戲。玩家扮演宏大戰役中的一名**地區指揮官**，
不在前線，只能透過「通訊」掌握戰況、對 NPC 小隊下達命令。

設計主軸：

- **你不在戰場**：所有資訊都來自部隊回報、偵察與推測，可能過時、可能錯誤。Discord 本身就是你的通訊介面。
- **部隊是有意識的個體**：每個小隊長都是會思考、會記憶、會成長、會違令的存在（由 LLM 扮演）。
- **戰場持續存在**：指揮官下線、部隊失聯，戰場依然運作。失聯不等於死亡。
- **戰役沒有終點**：你只是一個區域的指揮官，戰線永遠在推移。

## 2. 世界觀

- 時代：**現代以後**（近未來～科幻）。
- 前線作戰單位為**生化人／機器人**：
  - 避免與真人連結產生的倫理與邏輯破綻（陣亡、駭入、拆解、重編程都合理）。
  - 「記憶＝資料」「服從＝協議」，讓 LLM 扮演、偏離、記憶累積都有世界觀依據。
- 陣營：**待定**。

## 3. 戰役結構（宏大戰役）

```
最高司令部（系統）      戰略目標、增援與補給分配
   │
戰線（多個區域）        [A1][A2][A3]…  區域結果影響相鄰區域
   │
地區指揮官（玩家／AI）  只管自己的區域與交界
   │
小隊（NPC，可下令）     最小可控單位
   │
個體（NPC，不可操控）   有名字、狀態、記憶
```

- **永不結束**：戰線隨各區域勝負推移。
- **空缺由 AI 代理**：玩家可隨時加入／離開；下線時由 AI 指揮官代管，部隊會「感受到指揮官換人」。
- **分層模擬精度**：玩家所在區域精細模擬，遠方區域只做粗略數值推演（戰力 × 地形 × 補給）。
- 宏大戰役的**配兵與推演規則：待定**。

## 4. 單位設計

### 4.1 層級
- **小隊**：指揮官能直接下令的最小單位。有一名小隊長（LLM 扮演）。
- **個體**：小隊成員，不可操控，但有名字、傷勢、經驗、記憶。可能陣亡、可能接任隊長。

### 4.2 小隊屬性（初版）
| 屬性 | 說明 |
|---|---|
| 隊長角色卡 | 名字、個性、口頭禪、背景 |
| 出廠協議值 | 基礎服從度 |
| 偏離值 | 失聯、創傷、被遺棄等累積，降低服從 |
| 信任 | 指揮官過去命令的成敗影響 |
| 士氣／疲勞／彈藥／補給 | 戰鬥狀態 |
| 戰歷／記憶摘要 | 參與過的戰鬥、重要事件（供 LLM 扮演） |
| 隸屬 | 目前屬於哪位指揮官 |

### 4.3 去向
小隊會一直存在於戰場，直到：
- **陣亡**：頻道封存至「陣亡名冊」，保留戰歷。
- **運送回後方**：進入後備，可休整、修復、再部署。老兵可跨戰役保留。
- **失聯**：仍在戰場，依最後命令與自身個性自主行動。
- **被俘**：可能被救回、交換，或被敵方**駭入／重編程**收為己用。
- **整併**：失聯部隊遇到友軍殘部可合併，可能轉隸其他指揮官。
- **重置記憶**：可恢復服從，但失去經驗與個性（兩難選擇）。

### 4.4 老兵與風格
- 新出廠單位：沒有戰場經驗，**服從指揮官時存活率最高**。
- 被遺棄後再接回的部隊：會帶著自己的戰鬥風格，不再是純粹服從軍令。

## 5. 真相與認知分離

```
世界真相（引擎內部）              指揮官情報表（玩家可見）
Alpha 在 C4，剩 3 人，撤退中       Alpha：最後回報 B3，失聯 2 回合
敵軍一個排在 B4                    B4：疑似敵軍？（1 回合前偵察）
```

- 引擎只模擬**真相**。
- 每位指揮官（含 AI 指揮官、副官）只能存取自己的**情報表**，透過回報／偵察／截獲更新。
- Discord 只呈現情報表，「有限資訊」由架構保證。

## 6. 服從

舊版「服從度 = 出廠協議 − 偏離 + 信任」的數值已移除，改由 6.1 的信念／傾向決定。
服從仍由**引擎擲骰**（服從／變通／拒絕），LLM 只負責演出：

- 基準由「執行方式」傾向決定：literal 92、intent 78、own 55。
- 士氣低落、半數以上隊員倒下時下降；**危險命令**（LLM 判定 risky）額外下降。
- 每道命令同時擲「一般」與「危險」兩個結果，依 LLM 判定的 risky 採用其一。

### 6.1 信任與態度（已實作）

信任不做成單一數值，態度也不固定。三層結構：

```
① 經歷（引擎記錄，不可竄改）
   事實層：t / kind / text / mapped / outcome     ← 固定格式、客觀
   解讀層：interp（隊長當下自己寫的一句想法）    ← 自由文字、主觀，不分類
        ↓  反思（事件後觸發，由 LLM 扮演隊長自己）
② 信念（隊長自己歸納的句子，可新增、修改、遺忘）
        ↓
③ 傾向（每次反思重選的行為開關組合）
   請示傾向／驗證要求／主動性／執行方式（字面、意圖、自己的方式）
```

- **不使用固定評價標籤**（如「荒謬命令」）：同一事件不同隊長解讀不同。事實層只記引擎可驗證的東西
  （例如 `mapped=null`＝在小隊能力與可選行動中找不到對應）。
- **反思只在事件後觸發**，輸入只有經歷，玩家無法用嘴改變信念，只能用行動。
- **入侵懷疑**不寫死，世界觀說明中告知「敵方能偽造通訊」，由隊長在反思中自然產生；
  產生後引擎開啟「驗證要求」傾向（未來敵方偽造命令時可直接沿用）。
- **出廠協議**改為角色卡上的「初始信念」；**偏離**改為「信念中來自自身經驗、而非協議」的比例。
- 服從判定由引擎依「命令與信念／傾向的衝突 + 狀態」計算，數值不呈現給玩家或 LLM。
- 隊長內心解讀（interp）預設不顯示；已保存於經歷，GM 可用 `/ac_status <squad>` 查看，日後可開放顯示。

**實作細節**
- 反思觸發（排入佇列，脫離交戰後執行，同一小隊至少間隔 6 tick，每 tick 最多一支小隊反思）：
  交戰結束、隊員陣亡、任務成敗、通訊恢復、收到無法對應或要求確認的命令。
- 反思輸出：新的信念清單（最多 6 條，標記 protocol／experience）、四個傾向、一句長期記憶摘要、心聲。
  提示詞要求「信念慢慢改變」：一次通常只動 1～2 條，出廠信念需反覆重大經歷才會推翻。
- 傾向如何影響行為：
  - execution → 服從基準；verify → 危險命令先要求確認（`pending_confirm`），指揮官重申後才執行。
  - consult／initiative → 寫入提示詞，影響隊長是否請示、是否主動回報。
- 角色卡改用 `initial_beliefs`（出廠信念）、`experience_beliefs`（老兵既有看法）、`tendencies`、`long_memory`。
- 舊存檔中的 protocol／deviation／trust 欄位讀取時自動忽略。

### 6.2 命令理解（已實作）

- 指揮官訊息先分類：order／question／chatter。只有 order 會改變行動。
- order 帶有 `confidence`：high＝明確；low＝隊長用自己的理解詮釋，可能要求澄清或直接照理解執行
  （猜錯也照做，結果由引擎結算）；none＝能力清單與可選行動中找不到對應，行動不變。
- 小隊能力清單見 `engine/units.py`（步兵：突擊步槍、短距無線電、光學／熱感測、急救模組；無重武器、爆裂物、
  載具、支援火力）。

## 7. 引擎與 LLM 分工

**原則：引擎是裁判，LLM 是演員。**

```
引擎：計算局勢 → 列出可選行動 + 服從結果
  ↓
LLM（隊長）：讀角色卡、記憶、命令、局勢 → 輸出 JSON
  { "action": "...", "target": "...", "report": "..." }
  ↓
引擎：驗證 action 合法 → 結算 → 寫入事件與記憶
```

- LLM 不決定戰鬥結果，避免不一致與話術操弄。
- **只在關鍵時刻呼叫 LLM**：收到命令、接敵、恢復通訊、重大傷亡。其餘由規則驅動。
- **事件觸發時隊長可選擇不回報**（report＝null）：不回報則情報表不更新，「會不會主動回報」本身即是情報。
- 交戰中的次要事件（負傷、擊倒、彈藥見底）同一小隊至少間隔 3 tick 才觸發；重大事件（接敵、陣亡、
  彈藥打光、敵軍全滅、抵達）立即觸發。
- 移動可指定任一格與途經點，引擎以 BFS 尋路，預設繞開已知敵情；途中只在遇敵／出事／抵達時觸發隊長。
- 後端：9router（OpenAI 相容 API），連線設定放 `.env`（`LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`）。

## 8. 副官

給新手的輔助 LLM：

- 位於 `#指揮所`，以 embed 呈現**簡易現況**與 **2～4 個建議行動按鈕**＋「更新」按鈕。
- 按下建議按鈕＝以指揮官身分下達該命令，仍由小隊長解讀執行。
- **副官只讀指揮官情報表**，不會洩漏真相，也可能判斷錯誤。
- 只在重大事件後或玩家要求時更新。

## 9. 兵種與戰場物件（待定）

戰場上可能有：人（步兵）、機甲、火炮、車輛、航空器、地雷等。

**候選方案**：
- 所有可控單位都是「不同類型的小隊」，各有小隊長；類型差異以統一屬性表達：
  `{ 移動方式, 偵測範圍, 可攻擊對象, 弱點, 消耗 }`，形成相互剋制與協同需求
  （例：火炮需要他人提供座標；機甲需要步兵掩護；航空器怕防空）。
- **地雷等為「戰場物件」**而非單位：由某單位佈設後持續存在，敵我皆可能觸發，不可操控。

待討論：
- 混編小隊是否存在？
- 非人單位（無人機群、自動砲台）是否也有「意識」？
- 平衡方式。

MVP 只實作**單一步兵小隊**。

## 10. 時間系統

指揮官**不操控回合**。採「慢速即時」：

| 層 | 頻率 | 說明 |
|---|---|---|
| 模擬 tick | 隱藏，約 5～10 秒 | 移動、偵測、交火計算 |
| 行動耗時 | 遊戲時間 | 移動一格、交火持續等，決定實際節奏 |
| 回報 | 事件驅動 | 收令、接敵、狀態變化、恢復通訊時發言 |

- 命令隨時可下，進入佇列，在下一個 tick 生效（可有傳令延遲）。
- LLM 回應延遲自然成為「無線電延遲」。
- GM 保留手動推進 tick 的除錯指令。

## 11. 下令方式

- **直接打字**：在小隊頻道輸入自然語言命令，由小隊長（LLM）解讀。
- **副官按鈕**：新手可直接採用建議行動。
- **語音**：
  - 現階段：玩家使用本機聽寫功能（Windows `Win+H`、手機鍵盤麥克風）輸入文字，伺服器零負擔。
  - 未來：伺服器端 STT（可共用 kuro_bot 的 `lib/stt.py` 規劃），資源成本高，暫緩。

### 12.0 權限模型

| 對象 | 檢視 | 發言／按鈕 |
|---|---|---|
| @everyone | ✗ | ✗ |
| 所屬指揮官 | ✓ | ✓ |
| 被指揮官開放的人（情報共享） | ✓ | ✗（唯讀） |
| 「AC 觀戰」身分組（報到處按鈕自領） | ✓（所有指揮官分類） | ✗ |
| bot | ✓ | ✓（含 webhook） |

- 伺服器擁有者與管理員不受頻道權限限制，因此程式端另行檢查：只有所屬指揮官的訊息會被當作命令、
  副官按鈕只有本人能按。
- 情報表、副官以指揮官為單位，戰場真相共用。

| 狀態 | 呈現 |
|---|---|
| 正常 | 隊長以 webhook 回報 |
| 訊號差 | 訊息帶雜訊、延遲（未來） |
| 失聯 | 頻道靜止，最後訊息停留 |
| 恢復通訊 | 隊長補報失聯期間經過 |
| 被俘／叛變 | 頻道消失（未來） |
| 陣亡 | 封存（未來） |

### 12.1 Discord 限制與政策
- 每伺服器 250 身分組、500 頻道、每分類 50 頻道；每頻道 15 webhook。
- 全域 50 req/s（互動回應不計）；10 分鐘 10,000 次無效請求會被暫時封 IP。
- 頻道改名約每 10 分鐘 2 次 → **不用頻道名表達頻繁變化的狀態**。
- 不靠大量建立／刪除頻道作為遊戲機制。
- 政策：不得以多 token 規避速率限制（功能分工可）；不主動 DM；NPC 不冒充真人／官方；
  遊戲貨幣不得與真錢掛鉤；不得用訊息內容訓練 AI。
- 部隊數量增長時，考慮「一指揮官一頻道＋每小隊一討論串」。

### 12.2 指揮所數量的擴展問題（待解）

目前每位指揮官一個分類（指揮所＋每小隊一頻道），人數多時會撞上 500 頻道／分類數量上限。替代方向：

- **一指揮官一頻道＋小隊討論串**：指揮所為唯一頻道，每個小隊是私人討論串（頻道數 = 指揮官數）。
- **共用區域頻道＋私人討論串**：同一區域的指揮官共用一個區域頻道，各自的小隊用私人討論串（只邀請本人）。
- **DM／使用者安裝 App**：指揮介面移到私訊或 user-install 指令，伺服器只放公共戰況（需注意不主動 DM 政策，須玩家主動開啟）。
- **網頁／Activities 介面**：指揮細節移到 Discord Activities 或網頁，Discord 頻道只承載通訊與公共事件。
- **多伺服器分區**：每個戰區一個伺服器，bot 共用同一個核心。

MVP 先維持「每指揮官一分類」，待玩家數增加再選型。

## 14. MVP 範圍

**目標**：驗證「透過通訊與有意識的機器人小隊長合作」是否好玩。

- 單一場景（廢棄城區 3×3），隱藏敵軍巡邏。
- 單一步兵小隊（Alpha），LLM 扮演隊長。
- 直接打字下令；副官 embed + 建議按鈕。
- 隱藏 tick（10 秒）；事件驅動回報。
- 服從度計算。
- GM：`/ac_link off|on` 測試失聯與補報；`/ac_tick`、`/ac_status`、`/ac_squad_reset`。
- 存檔：JSON。

  可改為戰術地圖內具名區域（例如「塔基二樓」）。

### 16.2 網頁 vs Discord

- 朋友建議做成網頁；目前判斷：方向可能正確，但先把核心玩法做完再決定。
- 架構已分離：`engine/`（核心）與 `cmds/`（Discord 層）。換成網頁時 engine、LLM、角色卡、情報表／副官邏輯
  全部沿用，只需另寫網頁層（例如 FastAPI + 前端）。頻道權限、報到處、webhook 等 Discord 專屬部分不沿用。
- 各自優勢：網頁擅長地圖視覺化、大量單位、無頻道與速率上限；Discord 擅長「透過無線電指揮、不在戰場」的
  沉浸感、推播通知與社群。
- 可考慮混合：網頁做地圖與指揮介面，Discord 做小隊無線電通知與社群，兩者共用同一個 engine。
- 原則：在決定前避免再加 Discord 專屬功能，優先投資 engine。

### 16.1 舊版原型保留的構想

舊版 `cmds/AC.py` 與 `character/` 範本已移除（原始檔可在 kuro_bot git 歷史找到），以下構想留作參考：

- **等級**：`lvl` + `rank` 雙軸（可對應老兵經驗與軍階）。
- **雙貨幣**：`gss` 與 `coin`（可能對應軍需點數與一般貨幣）。
- **職業／技能**：`job`、`skill`。
- **NPC 個性**：`innate personality`（先天）與 `acquired personality`（後天）
  → 可對應「出廠協議／預設個性」與「戰場經驗造成的偏離」。
- **機體範本**：`AC_new_mecha`（`name`、`hp`），可作為兵種（機甲）設計起點。
- **舊世界頻道結構**：`start_world`（`start`、`edit` 文字頻道、`Create new world` 語音頻道）、
  `AC`（`start_menu`、`world` 文字頻道、`join_game`、`left_game` 語音頻道）
  → 語音頻道作為「進入即觸發」的大廳機制。
