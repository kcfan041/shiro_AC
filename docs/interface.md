# 網頁介面與呈現

網頁版（`server.py`、`web/`）的現況、資訊呈現原則，以及之後的呈現路線。
Discord 版介面已凍結，見 §6。
相關：[小隊長與 LLM](squad-llm.md)、[架構](architecture.md)。舊的完整方案在 [archive/web/](archive/web/)。

## 1. 原則

- **維持指揮官視角**：玩家下達意圖，小隊自己落實。畫面要幫玩家看懂命令怎麼被接收、解讀、執行，不是讓玩家修正每名隊員的位置。**不做單兵微操。**
- **資訊限制是玩法，不是 UI 缺陷**：畫面只呈現該指揮官當時合理取得的資訊。確認、推測、最後已知、聲音來源要有不同的視覺語彙。
- **迷霧在伺服器端過濾**：前端拿不到不該知道的東西，而不是拿到了再藏起來。GM 拿完整資料。
- **後端是權威裁判**：前端可以用更高更新率播放動畫，但不能自己決定命中、發現、傷亡、士氣或 AI 行動。
- **先可讀，再華麗**：看懂單位狀態 → 看懂命令與行動 → 看懂傷亡與轉折原因 → 節奏與情緒 → 美術品質。
- **行動理由只來自規則狀態**，不用 LLM 臨時杜撰戰鬥原因。

## 2. 現在的畫面

技術：aiohttp + 原生 JS（`app.js`、`world.js`、`events.js`、`dock.js`）+ Canvas（requestAnimationFrame）。

- **登入**：暱稱（1～16 字）＋密碼（≥4）。帳號存 `data/accounts.json`（PBKDF2），session 只在記憶體、7 天，cookie `ac_session`；也可用 `?token=` 登入連結。
- **報到處**：就任指揮官、觀戰、說明、登出。
- **指揮室**：
  - 左欄：**常駐戰術圖**（連續地圖時），鏡頭跟隨選中小隊，可拖曳、滾輪縮放、🎯「跟隨」切回；區域外調暗並顯示情報敵情。左上角**迷你作戰圖**，點了打開**作戰圖彈窗**（選格時自動開關）。
  - 中欄：**小隊卡片**——隊員（點名字看武器、熟練度、傷勢、參戰次數、是否帶過隊）、自主等級按鈕、無線電紀錄、快捷按鈕、下令回執、🚑 請求後送（有人倒地才顯示）、📻 友軍無線電、📦 請求補給、🗺 戰術畫面、提議「同意」、自主行動「取消」、帶著傷員的標示。
  - 右欄：即時戰況與事件、副官、任務。
  - 作戰圖點格子：格子資訊、🛩 派無人機偵察、🤝 請求友軍支援、哪支友軍正在支援這格。
  - 戰術畫面：子彈線、爆炸、煙霧、迷霧（看不到的敵人畫最後位置與經過秒數）、標定點、指揮部支援、戰鬥紀錄。
  - **回放**：每場交戰存回放（最近 20 場；連續地圖依交火的地方分段），在戰術畫面內播放。
  - 說明、GM 都是彈窗。GM：推進 tick、暫停、補預備兵池、重置、清空、切斷／恢復通訊、看某格真相、觀戰。
- **數據鏈**：通訊正常時自己小隊即時更新；失聯時停在最後資料（「📵 失聯｜T 的資料」），快捷按鈕停用。
- **時間變慢**：伺服器模擬跟不上時（降級 AI 後仍不夠），遊戲時間整體變慢，頂部列顯示「⏱ 時間 ×0.8」（近 10 秒平均，低於 0.95 才顯示）。
- **播放**：前端延後一個更新播放（正在播的影格播完才接下一格），子彈、爆炸、倒地在事件的真實時間出現；播放速度跟著實際收到影格的間隔走（佇列積兩格以上才稍微加速），回放每格長度＝涵蓋的戰鬥時間 ÷ 播放速度。
  個體依每一格的**起步與抵達時間**內插（`pst`／`pt`），還沒走到的那一格（`nx`、`nst`～`nt`）跨影格繼續往前推，所以一格 1.25 秒的移動是連續的，不會「停兩格影格、再在一格裡衝過去」。
- **戰鬥紀錄**：影格開始播時才寫進去（和畫面同步），前面標戰鬥時間（m:ss），每秒最多重畫一次；同一人 2.5 秒內的壓制射擊（兩波）只列一筆，「射線上有隊友」5 秒內只列一次。
- **戰術畫面底部進度條**：到下一個作戰 tick（5 秒；隊長、作戰層、完整狀態更新）。
- **推送**：每個執行步（0.5 秒）推無線電與戰術影格；每個作戰 tick（5 秒）推完整狀態；有事件時另外推。客戶端每 25 秒 ping，伺服器心跳 30 秒。
- 設定 `setting/web.json`：`host`、`port`、`gm`（GM 暱稱）、`starter_cards`、`max_commanders`、`tick_seconds`（5）、`tac_steps`（10，一步 0.5 秒）、`react_gap`（2）、`llm_max_per_minute`、`adjutant_min_interval`、`save_path`、`replays`、`accounts`、`zone_mode`、`allies`、`background`、`autostart_tick`、`threaded`（戰術層在專用執行緒）、`plan_workers`（平行規劃行程數）、`plan_budget`（規劃時間預算）。

## 3. 結構化事件與迷霧過濾

戰鬥時記錄結構化事件，經伺服器依情報過濾後送前端（`engine/replay.py`、`engine/views.py`）：

```json
{"seq": 812, "t": 31, "phase": "fire", "sub": 0, "type": "shot",
 "actor": "s1.alpha.2", "target": "e3", "aid": "a31.7", "grp": "t31-fire",
 "data": {"mode": "suppress", "ow": false, "rounds": 4, "weapon": "dmr",
          "frm": [52.3, 40.1], "to": [[60.2, 47.9]], "impact": ["cover"]}}
```

- `seq`：整場遞增。`t`：執行步。`ts`：事件的戰鬥時間（秒，對齊 0.05 秒；第 11 步前端依此播放）。`phase`：`pre`／`move`／`overwatch`／`post_move`／`fire`／`throw`／`care`／`end`／`support`；`sub`：移動小步。
- `aid`：因果 ID，串起射擊 → 命中 → 倒地／陣亡。`grp`：同時結算群組（同一時刻的射擊 `t<n>-fire<毫秒>`、只有警戒射擊時 `t<n>-ow<毫秒>`、爆炸 `t<n>-throw<毫秒>`），播放時不能暗示不存在的先後。
- 類型：`shot hit down kia suppress spot hear lost throw blast dazzled melee brace hold_fire flanked aid drag exit surrender transfer support posture`。
- 影格另外帶 `units[].why`（行動理由）、`supp`、`bracing`、`psub`，以及 `shots[].aid/ow/mode`。

迷霧過濾：

- 看不到的敵人：行動者和目標 ID 拿掉；射擊只留彈道後三分之一、去掉武器；看不到的人被命中、倒地、陣亡、架槍、換姿勢都不送。
- 聽到槍聲：只送引擎寫進情報的誤差位置。
- 敵方的情報事件、敵人的 `why` 與 `supp`、別人的支援都不送（煙幕都送）。
- 需要連線中的小隊才有即時資料。

## 4. 呈現路線（之後）

Phase 0（固定遭遇與基線）、Phase E（結構化事件、行動理由、迷霧過濾、前端戰鬥紀錄）已完成。接下來的方向，**每一步都要先有實測證據再做**：

1. **技術驗證**（等實測確認 Canvas 不夠用才做）：TypeScript + Vite + PixiJS；正式部署由 aiohttp 提供 build 產物，伺服器不跑 Node。先用固定回放資料、40 個單位、相機與三種特效壓測。Phaser 是替代候選。
2. **戰術垂直切片**：用一場代表性遭遇（四人小隊、兩入口建築、2～3 守軍、包抄或破門、一次煙幕或閃光、至少一人倒地、有急救或撤退、隊長有回報），做完整播放：移動、轉向、姿勢、射擊、彈著、煙霧、倒地、急救、拖行，加基本音效。即時與回放共用同一個 renderer。
3. **即時戰鬥與指揮可讀性**：播放佇列落後偵測與壓縮（不可略過傷亡、命令結果、情報變化）、命令生命週期（送出 → 理解 → 執行中 → 完成／中斷）、戰術意圖 overlay、個體行動理由、情報視覺語彙、多場交火事件列、戰後復盤（AAR）。
4. **角色呈現與產品化**（§5）、重連與校正、Playwright 流程測試。
5. 之後才是內容擴張：功能不同的小隊、區域控制與補給線、任務後果、教學。

**資訊層級**：預設只顯示戰況（接敵方向、交火區、傷亡）與小隊（意圖、路線、命令狀態）兩層；個體（姿勢、壓制、傷勢、理由）和細節（射線、彈著）透過選取、暫停、回放看。

**音效優先序**：無線電與接令 → 槍聲爆炸（依距離方向）→ 壓制受傷急救 → 環境 → UI → 音樂。音效精度不能超過情報精度。

**Unity**：只在產品確定需要完整 3D、多樓層、載具或下載式平台，**而且**網頁垂直切片做不到時，才做讀同一份回放的對照原型。不先重寫模擬。

驗收：測試者看完固定遭遇，不看說明能答對主要問題 80%（敵人從哪開火、第一名傷員怎麼倒的、誰在掩護誰在動、煙幕擋了誰、最近一道命令執行了沒）。

## 5. 角色呈現（Phase 4，沒有固定美術能力的前提）

- 角色層建立在戰場可讀性之上：拿掉頭像和髮色，玩家仍要看懂敵我、朝向、姿勢、武器、狀態。辨識不能只靠顏色（色覺差異）。
- 三層：**戰場小人**（可讀性優先，共用身體與動作，以髮型輪廓、主色、裝備區分）、**頭像**（存在感的主要來源，用在無線電、回執、事件、戰後報告）、**事件特寫**（後期選配，可關閉，不搶鏡頭）。
- 最小規格：4 方向的站、蹲、臥、倒地與基本移動／射擊；每名具名角色 4 張頭像（中性、緊張、受傷、堅定）。表情由可驗證狀態觸發，不由 LLM 決定。
- 資產取得順序：程式形狀佔位 → 暫用頭像驗證事件頻率 → 定 2～4 名代表角色 → 只委託代表角色的頭像 → 驗證方向數 → 定縮放後才委託戰場 sprite／骨架。
- 缺專屬資產時自動用共用模板，不阻止角色加入遊戲。
- 美術方向尚未決定的問題見 [待定問題](open-questions.md#介面與美術)。

## 6. Discord 版（凍結）

`bot.py` + `cmds/`，沒被要求就不改。介面：`#報到處`（就任、觀戰）、每位指揮官一個分類（`#指揮所`：任務看板 → 副官面板 → 任務短通知；每小隊一個頻道，隊長以 webhook 回報）、GM 指令（`/ac_squad_spawn`、`/ac_lobby`、`/ac_wipe`、`/ac_link`、`/ac_tick`、`/ac_run`、`/ac_status`、`/ac_tmap`、`/ac_squad_reset`）。
權限模型、Discord 限制與指揮所擴展的討論見 [archive/design.md](archive/design.md) §12。
