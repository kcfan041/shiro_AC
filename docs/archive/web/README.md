# Web 強化方案

本目錄記錄網頁版由「可玩的工程原型」提升為「可驗證產品體驗」的方向。方案不改變目前的核心定位：玩家是遠端指揮官，透過命令、情報與無線電影響戰場，而不是直接微操每一名隊員。

## 文件

- [web-enhancement-plan.md](web-enhancement-plan.md)：完整方案，包含體驗目標、技術架構、戰鬥呈現、里程碑、驗收方式與轉向 Unity 的判斷門檻。
- [engine-data-gap.md](engine-data-gap.md)：引擎已計算但未輸出的過程資料，以及 2.5 秒時間模型的評估方式。
- [character-presentation.md](character-presentation.md)：在沒有固定美術能力的前提下，逐步建立戰場角色、頭像與事件呈現。

## 決策摘要

1. 目前選擇先評估 A 方向：純遠端指揮與 2D Web 戰術呈現，不加入直接操作士兵。
2. 保留 Python 權威模擬、情報隔離、LLM 分工和既有戰鬥規則。
3. 目前主要缺口是引擎沒有輸出足夠的步內事件資料，尚無證據顯示 Python 模擬效能追不上畫面。
4. 2.5 秒暫不判定為過長或過短；先拆分模擬粒度、世界時間、網路間隔和播放時長，再以固定遭遇量測。
5. 前端採用 Node.js/npm 建置流程，目標技術為 TypeScript + Vite + PixiJS；仍先完成技術尖峰驗證。
6. 在模擬資料與畫面之間增加「呈現事件層」，讓轉向、瞄準、射擊、彈著、壓制、受傷和救援具有可控制的時間順序。
7. 角色呈現列入 Phase 4；正式美術方向確定前，以可替換的佔位資產驗證可讀性。
8. 以一場完整遭遇作為垂直切片，用玩家理解度、畫面效能和製作成本判斷 Web 是否足夠。
9. 僅在確認產品需要完整 3D、多樓層、載具或下載式平台，且 Web 垂直切片無法達標時，再製作 Unity 對照原型。

## 本方案不代表

- 不代表立即更換現有前端技術。
- 不代表一次重寫所有頁面。
- 不代表提高畫面更新率就等於提高模擬頻率。
- 不代表加入單兵微操。
- 不代表先製作大量美術資產再驗證玩法。
- 不代表永遠排除 Unity；而是先建立可比較的證據。
