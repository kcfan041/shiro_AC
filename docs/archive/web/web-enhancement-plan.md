# Web 強化執行方案

狀態：提案  
適用方向：A 方向，純遠端指揮與 2D Web 戰術呈現  
適用範圍：網頁版戰術畫面、指揮介面、網路呈現層與產品驗證  
不含範圍：本文件不直接改動戰鬥公式、AI 決策或戰役規則

本方案不把 Web 當成不可改變的原則，而是先驗證最符合現有玩法、重用既有核心最多的方向。若產品後續確定需要直接控制士兵、完整 3D、多樓層或載具，再依第 13 節門檻重新評估 Unity。

## 1. 背景與問題

目前網頁版已具備作戰圖、連續戰術地圖、迷霧、命令回執、支援、回放、任務與多人指揮等功能。後端同時處理個體位置、視線、彈道、壓制、姿勢、傷勢、戰術 AI、敵方情報與小隊自主行動。

現階段的主要落差不是「沒有模擬」，而是模擬結果尚未完整轉換成玩家可以辨識、理解和感受的事件。典型問題如下：

- 單位、地形、射擊和爆炸主要以 Canvas 幾何圖形呈現，辨識度與狀態表達有限。
- 一個戰術步包含多個因果事件，但畫面大多以位置補間和短暫線條播放。
- 玩家能看到結果，卻不一定知道單位為何停下、改道、沒有射擊或突然倒地。
- 無線電、任務、戰況和戰術畫面並存，但缺少一致的注意力層級。
- 區域有程序地圖差異，仍缺少足以形成記憶點的地標與場景語言。
- 現有原生 JavaScript 前端適合原型，但繼續加入資產、音效、粒子和動畫狀態會提高耦合。

因此，本方案先回答三個問題：

1. 如何讓玩家在不閱讀全部文字紀錄的情況下理解戰況？
2. 如何在不改為單兵微操的前提下增加戰鬥張力？
3. 如何用最小投資驗證 Web 是否足以支撐正式產品？

## 2. 產品原則

### 2.1 維持指揮官視角

玩家下達意圖，小隊自行落實。畫面應協助玩家理解命令如何被接收、解讀與執行，而不是要求玩家修正每一名隊員的位置。

### 2.2 資訊限制是玩法，不是 UI 缺陷

畫面只能呈現該指揮官在當時合理取得的資訊。最後已知位置、聲音來源、推測火力方向和確認目標必須具有不同視覺語彙，不能因追求華麗而洩漏真相狀態。

### 2.3 先提高可讀性，再提高華麗度

優先順序為：

1. 看懂單位狀態。
2. 看懂命令與行動關係。
3. 看懂傷亡與局勢轉折原因。
4. 建立戰鬥節奏與情緒。
5. 提升材質、粒子、鏡頭和美術品質。

### 2.4 模擬頻率與播放頻率分離

後端仍是權威裁判。前端可以用更高更新率播放動畫，但不得自行決定命中、發現、傷亡、士氣或 AI 行動。提高到 60 FPS 不代表後端必須以 60 Hz 模擬。

### 2.5 垂直切片先於全面重製

先完成一場包含完整因果鏈的代表性遭遇，再決定是否重製其餘畫面。不可先建立龐大框架、全部資產或完整戰役，最後才驗證戰鬥是否更有張力。

## 3. 目標與非目標

### 3.1 第一階段目標

- 玩家可在兩秒內辨識己方單位的移動、射擊、壓制、受傷與失能狀態。
- 玩家可從畫面和聲音理解主要威脅方向。
- 玩家可追蹤一項命令從送出、確認到實際執行的狀態。
- 一場交火至少能辨識接敵、僵持或機動、局勢轉折、脫離或結束等節點。
- 回放和即時戰鬥使用相同的呈現規則。
- 低階桌面裝置在代表性場景維持穩定畫面更新。
- 保留現有迷霧、情報隔離和伺服器權威結果。

### 3.2 非目標

- 不在第一階段加入完整 3D。
- 不在第一階段加入自由旋轉鏡頭或多樓層。
- 不加入逐兵框選和即時微操。
- 不重寫 Python 模擬核心。
- 不同時重製所有 HQ、GM、帳號與任務頁面。
- 不以粒子數量或貼圖解析度作為主要成功指標。
- 不先承諾手機具有與桌面相同的完整操作密度。

## 4. 目標體驗

### 4.1 戰鬥資訊層級

戰術畫面應依優先級分為四層：

| 層級 | 玩家問題 | 呈現內容 |
|---|---|---|
| 戰況 | 現在發生什麼？ | 接敵方向、交火區、傷亡、撤退、任務事件 |
| 小隊 | 我的命令如何執行？ | 戰術意圖、行進路線、壓制組／機動組、命令狀態 |
| 個體 | 為什麼這個人沒行動？ | 姿勢、壓制、傷勢、彈藥、急救、架槍、受阻原因 |
| 細節 | 剛才如何命中？ | 射線、彈著、掩體、爆炸、回放事件與時間軸 |

預設只顯示戰況與小隊層。個體和細節層透過選取、暫停或回放查看，避免所有資訊同時出現。

### 4.2 一場代表性遭遇

垂直切片固定使用一個可重播場景：

- 一支四人小隊接近有兩個入口的建築。
- 兩至三名守軍占據不同射界。
- 小隊先接敵，再建立壓制。
- 玩家下達包抄或破門意圖。
- 使用一次煙幕或閃光支援。
- 至少一人受傷或倒地。
- 出現急救、拖行或撤退。
- 隊長至少有一次無線電回報。

這個場景必須能以固定種子或既有回放重複播放，作為畫面、效能和玩家測試的共同基準。

### 4.3 張力來源

張力不依賴提高操作速度，而來自：

- 命令送出後的有限等待與不確定性。
- 敵情由模糊到確認的過程。
- 火力方向與安全路線的變化。
- 壓制組是否維持火力、機動組是否成功前進。
- 傷員是否能被救回。
- 隊長是否照辦、變通、拒絕或要求確認。
- 戰況惡化時玩家是否要投入支援、改令或撤退。

## 5. 建議技術架構

### 5.1 保留項目

- Python simulation 維持權威狀態。
- aiohttp 在垂直切片階段維持現狀。
- WebSocket 持續承載即時更新。
- 既有玩家視圖、迷霧和 replay filtering 保留。
- LLM 維持「演員」角色，不決定合法性與戰鬥結果。
- 現有原生前端在新戰術客戶端可替代前繼續可用。

### 5.2 前端技術方向

接受加入 Node.js 和 npm 建置流程。目標技術為 TypeScript + Vite + PixiJS：

- TypeScript 提供事件與網路資料的型別界線。
- Vite 提供模組、開發伺服器與資產建置。
- PixiJS 處理 sprite batching、相機、粒子、filter 與 WebGL 渲染。
- HTML/CSS 繼續處理文字密集的指揮、任務與設定介面。
- 開發時由 Vite 提供模組與熱更新；正式部署時由 aiohttp 提供 Vite build 的靜態產物，不要求 production server 執行 Node.js。

PixiJS 仍須經 Phase 1 技術尖峰驗證。Phaser 可作為替代候選；若實測顯示團隊更需要 scene、loader、audio 和 tween 的完整生命週期，而不介意框架約束，才改選 Phaser。

不建議第一階段採用完整 React 重寫。戰術 renderer 與一般 UI 可以獨立演進；是否採用 UI framework 應由 HQ 介面複雜度另行決定。

### 5.3 前端模組邊界

建議最小模組如下：

| 模組 | 責任 |
|---|---|
| transport | WebSocket 連線、序號、重連、snapshot 接收 |
| protocol | 訊息型別、版本與資料驗證 |
| world-state | 玩家可見狀態，不保存伺服器真相 |
| presentation | 將權威 frame 轉成有時間順序的表現事件 |
| renderer | 地圖、單位、特效、overlay 與相機 |
| audio | 空間化音效、無線電與音量優先級 |
| tactical-ui | 選取、tooltip、時間軸、命令狀態 |
| diagnostics | FPS、延遲、佇列、payload 與事件檢查 |

renderer 不解析業務規則；transport 不直接操作 sprite；UI 不推測未知敵人的真實位置。

## 6. 呈現事件層

### 6.1 目的

目前狀態影格適合保存權威結果，但不足以描述一個戰術步應如何播放。呈現事件層位於 simulation frame 和 renderer 之間，負責排序、持續時間與視覺提示，不改變結果。

這些事件不能只由前端根據起點和終點猜測。警戒射擊、一般射擊、壓制來源、急救關係和同時結算語意必須由後端在模擬發生時記錄，再經玩家視圖過濾。詳細缺口與時間模型見 [引擎與畫面資料缺口](engine-data-gap.md)。

概念資料如下：

```json
{
  "sequence": 1842,
  "duration_ms": 2500,
  "events": [
    {"at_ms": 80, "type": "turn", "actor": "alpha-2", "facing": 1.57},
    {"at_ms": 240, "type": "brace", "actor": "alpha-2"},
    {"at_ms": 520, "type": "fire", "actor": "alpha-2", "target_hint": "east-window"},
    {"at_ms": 590, "type": "impact_cover", "position": [42.2, 18.4]},
    {"at_ms": 640, "type": "suppressed", "actor": "known-enemy-3"},
    {"at_ms": 920, "type": "move_start", "actor": "alpha-3"},
    {"at_ms": 1730, "type": "down", "actor": "alpha-3"}
  ]
}
```

這只是協定方向，不是固定 schema。正式實作前必須確認哪些資料可由既有 frame 安全推導，哪些必須由後端在事件發生時記錄。

### 6.2 事件分類

| 分類 | 事件範例 | 主要回饋 |
|---|---|---|
| 感知 | 發現、失去目標、聽見射擊 | 標記、音效、情報樣式變化 |
| 姿態 | 轉向、蹲下、臥倒、架槍 | 單位動畫、輪廓變化 |
| 移動 | 起步、衝刺、停下、路線受阻 | 路線、速度、塵土、原因提示 |
| 火力 | 瞄準、開火、彈著、裝填 | 火光、聲音、曳光、掩體反應 |
| 效果 | 壓制、受傷、倒地、死亡 | 狀態、音效、短暫聚焦 |
| 協作 | 急救、拖行、交接物資 | 連結線、進度、動作狀態 |
| 指揮 | 接令、變通、改戰術、撤退 | 命令卡、無線電、意圖 overlay |
| 支援 | 煙幕、無人機、空投 | 預告區、到達時間、區域效果 |

### 6.3 播放規則

- 每個事件含穩定 sequence，避免重連或重送造成重複播放。
- 狀態 snapshot 可直接校正畫面，事件只負責從前一狀態過渡。
- 前端落後時可壓縮非關鍵移動，但不可略過傷亡、命令結果與情報變化。
- 切換分頁後返回時先同步最新 snapshot，不高速播放所有過期粒子。
- 即時模式不可透過慢動作拖累權威模擬；事件聚焦只能在有限緩衝內調整播放。
- 回放模式可暫停、逐事件前進與改變速度。

## 7. 視覺與音效方案

### 7.1 視覺方向

第一階段採清晰的戰術圖像，而不是追求擬真：

- 地形使用一致 tile atlas，建立道路、牆面、門窗、瓦礫、植被和掩體分類。
- 單位使用方向性 sprite 或簡化骨架，至少涵蓋站、蹲、臥、倒地。
- 己方、友軍、確認敵軍、推測敵軍和最後已知位置使用不同輪廓，不只改顏色。
- 射擊由槍口火光、有限曳光和材質相符的彈著組成，不讓每發子彈都成為長亮線。
- 壓制以單位反應、掩體附近彈著和短暫 UI 提示呈現，避免全螢幕特效長時間遮蔽。
- 煙霧同時表達遮蔽範圍和濃度，但不暴露玩家未知的精確邊界。
- 地標使用少量手工場景物件建立區域記憶點。

### 7.2 Overlay 原則

Overlay 必須可分層開關：

- 戰術意圖：固守區、壓制方向、包抄側、撤退出口。
- 命令進度：送出、收到、確認、執行、完成或失敗。
- 情報：確認、推測、最後已知、聲音來源。
- 單位狀態：選取後顯示，不常駐所有數值。
- 支援：落點、預估到達、有效區域和風險警告。
- 回放：關鍵事件、傷亡、戰術切換和命令時間。

### 7.3 音效優先級

本專案以通訊為核心，音效投資順序建議為：

1. 無線電提示、接令、緊急呼叫與失聯。
2. 不同距離和方向的槍聲、爆炸與彈著。
3. 壓制、受傷、倒地和急救提示。
4. 環境底噪與區域辨識音。
5. UI 操作與任務提示。
6. 音樂與動態配樂。

音效不能洩漏不可知敵軍的精確位置。若引擎只允許玩家知道大致聲源，前端也只能提供相應精度。

### 7.4 相機語言

- 平時跟隨選中小隊，保留拖曳和縮放。
- 接敵時只做輕微提示，不強制奪走玩家鏡頭。
- 首次傷亡、突破或撤退可提供可取消的事件聚焦。
- 多場交火同時發生時，以事件列讓玩家選擇，不自動來回跳轉。
- 回放可提供關鍵事件跳點。

## 8. 指揮介面強化

### 8.1 命令生命週期

每項命令應具有一致狀態：

```text
草擬 -> 已送出 -> 已接收 -> 已理解 -> 執行中 -> 完成／中止／失敗
```

服從結果仍維持現有分類，例如照辦、變通、拒絕和要求確認。UI 必須區分「命令未收到」「已收到但尚未行動」及「行動被戰況阻止」。

### 8.2 行動理由

選取單位時可顯示由規則產生的短理由，不暴露人格數值或隱藏機率：

- 射線上有友軍，暫停射擊。
- 缺少可用掩體，等待煙幕。
- 遭到壓制，無法安全推進。
- 隊友倒地，正在前往急救。
- 彈藥不足，降低射擊頻率。

理由應來自可驗證的模擬狀態，不使用 LLM 臨時杜撰戰鬥原因。

### 8.3 戰後復盤

既有回放應逐步擴充為 AAR：

- 命令與戰術切換時間線。
- 首次發現與情報失效時間。
- 主要火力方向。
- 傷亡、誤擊與救援原因。
- 支援使用與效果。
- 關鍵轉折書籤。
- 小隊消耗與任務結果摘要。

AAR 是驗證 AI 可理解性的重要工具，也能把模擬深度轉換成玩家學習。

## 9. 網路與效能方向

### 9.1 訊息分頻

長期建議將訊息分為：

- 低頻 snapshot：任務、隊員資訊、小隊 metadata。
- 中頻 world delta：位置、姿勢、可見性和效果狀態。
- 事件 stream：射擊、命中、命令、無線電和關鍵事件。
- 靜態資料：地圖、資產 manifest 和不常變動的定義。

垂直切片不必一次完成所有 delta protocol，但所有新訊息應預留 `protocol_version`、`sequence` 和 server time。

### 9.2 重連與校正

- 連線恢復後取得最新權威 snapshot。
- 依 sequence 忽略重複與過期事件。
- 前端座標偏差以短時間平滑校正；傷亡、可見性等離散狀態立即校正。
- 無法補齊事件時，寧可跳到當前狀態，不推測缺失戰鬥結果。

### 9.3 預算

垂直切片先採下列暫定預算，實測後調整：

| 項目 | 暫定目標 |
|---|---|
| 桌面畫面更新 | 代表場景穩定 60 FPS；低階裝置至少穩定 30 FPS |
| 主執行緒 frame time | 60 FPS 目標下多數 frame 小於 16.7 ms |
| 操作回饋 | 本地按鍵或點擊 100 ms 內出現已送出狀態 |
| 關鍵事件延遲 | 收到權威事件後 150 ms 內進入播放佇列 |
| 記憶體 | 30 分鐘代表場景無持續成長趨勢 |
| 重連 | 測試環境中 5 秒內恢復可操作 snapshot |

這些不是 SLA，而是判斷架構方向的測試標準。

## 10. 實施階段

### Phase 0：基線與成功條件

預估：1 週。

產出：

- 固定代表性遭遇與 replay fixture。
- 現有版本錄影、FPS、payload、模擬步時間和玩家理解度基線。
- 目標裝置與瀏覽器清單。
- 五至八項核心事件的視覺草圖。
- 確認產品維持小隊級意圖控制。

退出條件：團隊可用同一場遭遇描述「目前不足」和「改善後應看懂什麼」。

### Phase E：後端事件記錄

預估：1 至 2 週。

此階段只增加呈現資料，不改變戰鬥結果。詳細規格見 [引擎與畫面資料缺口](engine-data-gap.md)。

產出：

- 最小結構化事件 schema，包含 phase、substep、sequence 和事件關係。
- 警戒射擊、一般射擊、壓制、命中、倒地、急救、拖行與投擲事件。
- 同時結算群組，避免播放順序暗示錯誤因果。
- 玩家視圖事件過濾，不洩漏不可見敵軍。
- 新舊 frame 欄位並存，讓現有前端繼續運作。
- 固定種子結果一致性與事件權限測試。

退出條件：固定遭遇能輸出足以重建主要戰鬥過程的事件，且加入記錄前後的戰鬥結果完全一致。

### Phase 1：技術尖峰

預估：1 至 2 週。

產出：

- Node.js、npm、TypeScript、Vite 和 PixiJS 的最小建置流程。
- PixiJS 與固定 replay 資料的最小整合，先不接即時 WebSocket。
- Vite build 產物可由 aiohttp 靜態提供的部署驗證。
- 地圖、40 個單位、相機縮放和三種特效壓力測試。
- 資產載入與釋放驗證。
- Canvas fallback 或不支援 WebGL 時的錯誤處理決策。
- PixiJS 與 Phaser 的一次性比較記錄。

退出條件：選定 renderer，確認代表裝置達成最低 FPS，且沒有阻斷現有情報隔離的架構問題。

### Phase 2：戰術垂直切片

預估：3 至 5 週。

產出：

- 戰術地圖與單位 sprite。
- 移動、轉向、姿態、射擊、彈著、煙霧、倒地、急救和拖行表現。
- 呈現事件佇列。
- 相機與基本 overlay。
- 無線電、武器、彈著和傷亡音效。
- 即時與回放共用 renderer。
- 診斷 overlay。

退出條件：代表性遭遇能在獨立回放播放器中從開始到結束完整播放，不依賴舊 Canvas 才能理解主要戰況。

### Phase 3：即時戰鬥與指揮可讀性

預估：2 至 3 週。

產出：

- 將已驗證的回放事件播放器接上 WebSocket 即時 frame。
- 播放佇列落後偵測、事件壓縮和 snapshot 校正。
- 命令生命週期。
- 小隊戰術意圖 overlay。
- 個體行動理由。
- 情報狀態視覺語彙。
- 多場交火事件列。
- 初版 AAR 時間線。

退出條件：測試者可說明命令如何影響戰況，以及至少八成主要傷亡的直接原因。

### Phase 4：角色呈現與產品化

預估：依測試和資產取得方式拆分。角色規格與無美術能力時的導入順序見 [角色呈現方案](character-presentation.md)。

產出：

- 可替換的戰場角色模板、角色 ID、職責和小隊辨識。
- 4 方向的站、蹲、臥、倒地與基本移動／射擊；是否升為 8 方向由實測決定。
- 頭像欄位、表情狀態、fallback 圖和無線電事件綁定。
- 受傷、急救、拖行與失聯的角色化呈現。
- responsive layout 和輸入方式整理。
- 資產 manifest、版本和快取策略。
- WebSocket 重連、sequence 和 snapshot 校正。
- Playwright 關鍵流程測試。
- 視覺回歸或固定 replay 截圖測試。
- 舊戰術 renderer 的移除條件與回退方案。

角色美術未定時先使用程式形狀或佔位 sprite。正式資產優先投資頭像與表情，再決定逐格 sprite、2D 骨架或混合方式，避免美術成為 Phase 2-3 的阻塞。

退出條件：新 renderer 可作為預設，核心流程都有自動化檢查；缺少專屬角色資產時仍能使用共用模板完整遊玩。

### Phase 5：完整配套系統

本階段屬產品擴張，不與 renderer 重製綁在同一里程碑。建議順序：

1. 偵察、火力、工兵等功能差異明確的小隊。
2. 區域控制與補給線。
3. 可選任務與持續後果。
4. 傷員、補員、裝備和休整。
5. 小隊檔案、戰歷與戰後報告。
6. 教學戰役與正式 onboarding。

## 11. 測試與驗收

### 11.1 玩家理解度

每位測試者觀看或遊玩代表性遭遇後回答：

- 敵人主要從哪裡開火？
- 哪個單位負責壓制，哪個單位正在機動？
- 最近一項命令是否已被接收和執行？
- 第一名傷員如何受傷？
- 小隊為何停止推進或改變路線？
- 支援是否達到預期效果？

第一輪目標：未經開發者解釋時，主要問題答對率達 80%。

### 11.2 體驗指標

- 接敵後兩秒內能辨識威脅大致方向的玩家比例。
- 能正確描述命令狀態的玩家比例。
- 因資訊過多而暫停或迷失的次數。
- 玩家主動查看個體理由和 AAR 的頻率。
- 玩家是否在意具名隊員的受傷與救援。
- 玩家認為等待是緊張、合理或純粹停滯。

### 11.3 工程測試

- 固定 replay 的事件順序測試。
- 迷霧過濾後不可見實體不被 renderer 建立的測試。
- snapshot + event 重送、漏送與亂序測試。
- 分頁切換、背景恢復與重連測試。
- 30 分鐘記憶體與物件數 soak test。
- 40、100、200 個單位的 renderer benchmark。
- Chromium、Firefox、Edge 的主要流程測試。
- 低階整合顯示晶片與高 DPI 螢幕測試。

## 12. 風險與控制

| 風險 | 結果 | 控制方式 |
|---|---|---|
| 畫面變華麗但仍看不懂 | 投資沒有改善核心體驗 | 每個特效對應一項玩家問題，先做理解度測試 |
| 前端自行推測戰鬥 | 回放與即時結果不一致 | 權威結果只來自 server，事件層只控制播放 |
| 動畫排隊造成落後 | 玩家看到過時戰況 | 設定佇列上限，壓縮非關鍵事件並用 snapshot 校正 |
| 特效洩漏敵情 | 破壞迷霧玩法 | 所有事件先經玩家視圖過濾，建立不可見資訊測試 |
| 全面重寫拖慢玩法驗證 | 長期沒有可玩的版本 | 以新舊 renderer 並存和垂直切片逐步替換 |
| 美術資產需求失控 | 時程和成本膨脹 | 先定單一視覺語言與 atlas 預算，再擴充地區 |
| 行動理由與 AI 實際狀態不符 | 玩家失去信任 | 理由只能由規則狀態產生，不以 LLM 補寫因果 |
| 桌面可用但窄螢幕崩壞 | 限制可達性 | Phase 4 定義資訊折疊，不強塞三欄版面 |

## 13. Unity 評估門檻

完成 Phase 2 和至少一輪玩家測試前，不啟動完整 Unity 遷移。符合以下多項條件時，才製作 Unity 對照原型：

- 產品確認需要完整 3D，而非 2D 或 2.5D。
- 多樓層、載具、角色骨架動畫或場景破壞是核心玩法，不只是視覺願望。
- 目標平台以 Steam、桌面或主機為主，瀏覽器即玩不再重要。
- 團隊已有或能持續配置 Unity、3D 美術和技術美術能力。
- Web 垂直切片在目標硬體無法達成效能或視覺需求，且問題不是資產品質或呈現設計。
- 雙技術棧和 client 發布成本可被接受。

Unity 對照原型應只讀取同一份 replay 或事件 stream，不先重寫模擬。比較項目包括：

- 相同遭遇的製作工時。
- 畫面品質與玩家理解度。
- 資產迭代效率。
- 啟動時間、build 體積與最低硬體。
- 除錯、重播與自動化測試能力。
- 部署更新和團隊維護成本。

只有 Unity 在目標品質上有顯著且可持續的優勢，才進一步討論正式 client；Python 權威核心是否重寫是另一個獨立決策。

## 14. 決策檢查點

### Checkpoint A：技術尖峰後

決定 PixiJS、Phaser 或停止 WebGL 重製。依據是代表裝置效能、開發複雜度與現有資料整合，不依個人偏好。

### Checkpoint B：垂直切片後

決定是否擴展到完整戰術畫面。依據是理解度、張力、效能與資產成本。

### Checkpoint C：玩家測試後

決定下一筆投資應放在畫面、命令互動、戰役內容或引擎對照原型。不可把內容不足直接歸因於 Web。

### Checkpoint D：產品平台確定後

只有在平台、視覺目標、團隊能力與商業模式明確後，才重新比較純 Web、Unity client + Python server 或其他方案。

## 15. 尚待產品決策

開始 Phase 1 前應確認：

1. 首發平台是瀏覽器、Steam，還是兩者並行？
2. 視覺目標是戰術符號、2D、2.5D 還是完整 3D？
3. 玩家是否永遠維持小隊級命令，不加入單兵微操？
4. 一場戰鬥預期同時出現多少個體與多少個活動區域？
5. 手機是完整支援、唯讀觀戰，還是不在首發範圍？
6. 沒有固定美術能力時，正式資產預計採素材商店、委託或混合方式？
7. 戰場角色採逐格 sprite、2D 骨架或混合方式？
8. 最希望對標的三個遊戲或畫面影片是什麼？
9. 戰鬥張力最重要的來源是資訊不全、永久傷亡、資源壓力、多人協作，還是快速操作？
10. 2.5 秒目前只是網路／播放間隔，還是也要作為明確的遊戲時間尺度？模擬粒度和 AP 是否需要重定義？

## 16. 建議的近期工作順序

1. 鎖定代表性遭遇和固定 replay。
2. 錄下現有版本，建立理解度與效能基線。
3. 定義最小呈現事件 schema，補上後端事件記錄與玩家視圖過濾。
4. 畫出五至八個核心事件的低成本動態草圖。
5. 建立 Node.js/npm、TypeScript、Vite 和 PixiJS 技術尖峰，不先重製 HQ。
6. 先完成獨立回放播放器和戰術垂直切片。
7. 再接上 WebSocket 即時戰鬥，量測播放佇列與 2.5 秒時間模型。
8. 使用可替換佔位角色進行五至十位目標玩家測試。
9. 根據證據決定全面強化 Web、調整時間模型、投入角色美術，或製作 Unity 對照原型。

本方案的核心不是「堅持使用 Web」，而是先用最低重寫風險證明：目前成熟的模擬能否透過更好的事件呈現、資訊設計和音畫回饋轉化為玩家感受到的戰鬥張力。
