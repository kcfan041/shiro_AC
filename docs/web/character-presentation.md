# 角色呈現方案

狀態：Phase 4 規劃  
適用方向：A 方向，純遠端指揮與 2D Web 戰術呈現  
前提：開發者目前沒有固定美術製作能力，角色最終風格尚未決定

## 1. 目的

角色呈現不是把一般戰術棋子換成動漫臉，而是讓玩家在遠端指揮的限制下仍能感受到：

- 現在是誰在行動或回報。
- 每名隊員的職責、狀態和位置。
- 誰正在服從、變通、受阻、受傷或救援隊友。
- 傷亡影響的是具名角色，而不是可替換的數字。

角色層必須建立在戰場可讀性之上。即使移除頭像、髮色和角色名稱，玩家仍應看懂敵我、朝向、姿勢、武器和狀態；角色美術負責增加辨識、情感和記憶，而不是掩蓋資訊設計問題。

## 2. 三層呈現

### 2.1 戰場角色

平常顯示在戰術地圖上的小型角色。優先任務是可讀性：

- 一眼辨識敵我和所屬小隊。
- 看出朝向、站立、蹲下、臥倒和倒地。
- 看出移動、射擊、架槍、壓制、急救與拖行。
- 在一般縮放層級辨識隊長、火力手、射手和醫療職責。
- 選取時能對應到角色頭像與名字。

第一版不要求每名角色都有完全不同的全身動畫。可共用身體與動作，只以髮型輪廓、主色、裝備和頭頂識別區分。

### 2.2 頭像與立繪

角色存在感的主要來源，用於：

- 無線電回報。
- 命令接收與服從結果。
- 接敵、受傷、失聯、救援和撤退等事件。
- 小隊卡、人物狀態與戰後報告。
- 隊長反思、信念與戰歷。

頭像比戰場小人更容易表現表情和個性。在資源有限時，應優先投資頭像，而不是為每名角色製作獨立全套戰場動畫。

### 2.3 事件特寫

後期選配，不屬於首批角色資產：

- 首次重傷或救援成功時的短暫事件卡。
- 破門、支援或關鍵戰術切換的小型 cut-in。
- 回放中的角色關鍵事件書籤。

事件特寫必須可關閉，而且不能中斷其他交火或強制搶走鏡頭。

## 3. 戰場最小規格

### 3.1 無正式美術的驗證版

使用程式形狀或自製簡單佔位圖：

- 身體：方向明確的簡化輪廓，而不是圓點。
- 武器：突擊步槍、輕機槍、射手步槍、霰彈槍使用不同長度和輪廓。
- 姿勢：站、蹲、臥、倒地使用不同高度或外框。
- 個體：髮型剪影或背部識別色塊。
- 職責：小型、可關閉的隊長、火力、射手、醫療標記。
- 狀態：壓制、受傷、急救、失聯以動畫或輪廓表現，不只使用文字。

這一版的目的是驗證在目標縮放下能否看懂，不是評估最終美術品質。

### 3.2 正式 2D 戰場資產

若使用方向性 sprite，每個共用身體模板的最低需求可先限制為：

| 類型 | 最低內容 |
|---|---|
| 方向 | 4 方向；若斜向辨識不足再升為 8 方向 |
| 靜止 | 站、蹲、臥 |
| 移動 | 站立移動、蹲行、匍匐 |
| 戰鬥 | 瞄準、射擊、架槍或支撐射擊 |
| 狀態 | 壓制反應、受傷、倒地 |
| 協作 | 急救、拖行可先使用簡化姿勢與關係線 |

不建議一開始為每名角色、每把武器、每個方向手繪完整動畫。較可行的組合方式是：

- 共用身體動畫。
- 武器和少量裝備分層。
- 頭部、髮型或色彩作為角色差異。
- 以 shader 或 palette swap 表現小隊識別。
- 特殊角色只在頭像和少量配件上獨特化。

### 3.3 Sprite 與骨架動畫選擇

| 方案 | 優點 | 缺點 | 建議用途 |
|---|---|---|---|
| 逐格 sprite | 像素與手繪風格穩定、播放簡單 | 方向和動作增加時資產量快速膨脹 | 角色尺寸小、動作有限 |
| 2D 骨架動畫 | 可重用動作、替換裝備和髮型 | 綁定、切圖和變形需要專業能力 | 半 Q 版、角色尺寸較大 |
| 混合方式 | 身體骨架、特效逐格，兼顧重用和質感 | 管線最複雜 | 美術方向穩定後評估 |

PixiJS 本身是 renderer，不會自動提供角色骨架資產。若採 2D 骨架，需要另行評估 Spine、DragonBones 或其他 runtime 的成本、授權與 PixiJS 相容性。

## 4. 頭像與表情最小規格

每名具名角色第一批可只製作：

- 一張中性頭像。
- 一張緊張或接敵表情。
- 一張受傷或疲憊表情。
- 一張堅定或完成任務表情。

可選第五張：

- 角色個性專屬表情，例如不滿、害怕、逞強或冷靜。

表情切換必須由可驗證狀態觸發，例如接敵、壓制、受傷、士氣、拒絕或任務完成。LLM 可以產生台詞，但不能自行決定角色是否受傷或遭壓制。

## 5. 不會美術時的資產路線

| 路線 | 適合階段 | 相對成本 | 主要風險 |
|---|---|---:|---|
| 程式形狀和自製佔位圖 | Phase 2-3 | 低 | 無法評估最終角色吸引力 |
| 商店 sprite／UI／頭像素材包 | 原型和早期公開測試 | 低至中 | 風格與授權不一致，難表現原創角色 |
| 委託頭像與表情 | 角色方向確認後 | 中 | 需要角色設定與清楚規格 |
| 委託戰場 sprite 或骨架切圖 | 戰場規格穩定後 | 中至高 | 動作數和方向數容易使成本失控 |
| AI 生成概念圖 | 探索風格 | 低至中 | 一致性、可編修性、來源與商用授權風險 |
| AI 圖直接作正式資產 | 不建議預設採用 | 表面低、後續可能高 | 角色一致性、權利、平台規範與信任問題 |
| Spine／Live2D 動態立繪 | 後期加值 | 高 | 需綁定、參數和 runtime 授權能力 |

委託價格受地區、品質、用途、商用權、修改次數和交付格式影響很大，不宜在技術方案中當成固定預算。評估時至少要分開詢價：

- 頭像／胸像和表情差分。
- 全身立繪。
- 戰場 sprite sheet。
- 2D 骨架切圖和 rig。
- Spine／Live2D 動態製作。
- 商用授權、宣傳用途和著作權安排。

## 6. 建議取得順序

1. 用程式形狀或單色剪影完成事件播放和狀態可讀性。
2. 用一套暫用頭像驗證無線電、命令和傷亡事件的位置與頻率。
3. 定義 2 至 4 名代表角色的髮型、主色、裝備和個性。
4. 只委託代表角色的頭像與表情，不先製作全員立繪。
5. 以一個共用戰場身體模板測試 4 方向和 8 方向的必要性。
6. 確認鏡頭縮放與角色尺寸後，再委託正式 sprite 或骨架資產。
7. 試玩證明事件特寫有價值後，才增加 cut-in、Live2D 或 Spine 表演。

這個順序避免在 renderer、縮放和動作需求尚未穩定時購買無法使用的資產。

## 7. 角色辨識規則

角色辨識不能只依賴髮色。建議使用多重線索：

| 資訊 | 戰場呈現 | UI 呈現 |
|---|---|---|
| 個體身份 | 髮型輪廓、配件、短呼號 | 頭像、姓名、呼號 |
| 所屬小隊 | 腳下輪廓、臂章或背部色塊 | 小隊色條 |
| 職責 | 武器輪廓、裝備、可關閉職責標記 | 兵科圖示和武器 |
| 朝向 | 身體和武器方向 | 選取後射界或朝向線 |
| 姿勢 | 站、蹲、臥的輪廓高度 | 狀態文字只作輔助 |
| 傷勢 | 動作受限、受傷輪廓、頭像表情 | 部位傷勢與處置狀態 |
| 心理／服從 | 不直接用數值顯示 | 台詞、命令狀態、表情 |

需提供不依賴紅綠顏色的辨識方式，避免色覺差異造成敵我和狀態判讀問題。

## 8. 角色與事件的連結

角色層應消費結構化戰鬥和指揮事件，而不是掃描文字：

```text
命令送出 -> 隊長頭像顯示接收 -> 回覆台詞 -> 戰場意圖 overlay
接敵 -> 發現者短促回報 -> 戰場標記 -> 小隊轉向
壓制 -> 角色姿勢反應 -> 緊張表情 -> 必要時回報受阻
受傷 -> 戰場倒地 -> 傷者／隊長回報 -> 小隊卡更新
急救 -> 救援關係線 -> 進度或狀態 -> 完成／中斷回報
```

同一事件不應在戰場、頭像、文字和音效四處重複搶注意力。需要建立優先級：

1. 緊急傷亡與失聯。
2. 命令要求確認、拒絕或重大變通。
3. 新接敵和撤退。
4. 一般受阻、壓制和支援抵達。
5. 例行移動和狀態更新。

## 9. Phase 4 範圍

Phase 4 的最小交付建議為：

- 一套可替換的戰場角色模板。
- 4 方向站、蹲、臥、倒地與基本移動／射擊。
- 角色 ID、職責和小隊辨識。
- 頭像欄位、4 種表情狀態和 fallback 圖。
- 無線電事件綁定頭像、名字與戰場位置。
- 受傷、急救、拖行和失聯的角色化呈現。
- 資產 manifest，讓新角色可由資料註冊，不修改 renderer。
- 缺少專屬資產時自動使用共用模板，不阻止角色加入遊戲。

Phase 4 不包含：

- 每名角色完全獨立的戰場動畫。
- Live2D／Spine 全身動態立繪。
- 大量事件 CG。
- 語音配音。
- 社交或養成系統。
- 角色美術風格的最終定案。

## 10. 驗收方式

### 戰術可讀性

- 不看文字時，玩家能辨識姿勢、主要職責和受傷狀態。
- 四名隊員集中時，玩家能在兩秒內找到指定角色。
- 角色差異不降低敵我和迷霧判讀。
- 關閉頭像和立繪後，戰場仍可操作。

### 角色存在感

- 玩家能將至少一項關鍵事件與角色名字連結。
- 玩家知道誰回覆了命令、誰受傷、誰前往救援。
- 戰後能回想至少兩名隊員在戰鬥中的不同作用。
- 頭像事件頻率不遮蔽戰場，也不讓玩家疲乏。

### 生產可行性

- 新增角色不必製作整套獨立動作。
- 缺少美術資產時有 fallback，不阻塞功能測試。
- 資產授權、來源和商用限制有可追蹤紀錄。
- renderer 不依賴特定角色尺寸或單一素材包。

## 11. 尚待決策

- 戰場小人的比例：Q 版、半 Q 版或正常比例簡化。
- 方向數：4 方向是否足夠。
- 美術基調：可愛、戰術系、壓抑或混合。
- 頭像尺寸和事件出現位置。
- 是否需要全身立繪，或胸像已足夠。
- 正式資產採商店素材、委託或混合方式。
- 是否採用骨架動畫，以及對應 runtime 和授權。
- AI 生成內容是否只限內部概念階段。

在上述問題決定前，Phase 2 和 Phase 3 應使用可替換的佔位資產，避免角色美術成為 Web 強化的前置阻塞。
