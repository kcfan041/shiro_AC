# 引擎與畫面資料缺口

狀態：評估提案  
適用方向：A 方向，純遠端指揮與 2D Web 戰術呈現  
相關文件：[Web 強化執行方案](web-enhancement-plan.md)

## 1. 結論

目前最主要的問題不是底層引擎算不動，也不是畫面更新率高於模擬更新率，而是：

> 模擬內部已經發生的步驟、因果與關係，沒有被完整保存成可供畫面播放的資料。

戰術引擎在一個 step 內已處理轉向、移動微步驟、偵測、警戒射擊、一般射擊、壓制、命中、投擲、急救與拖行。現有回放主要保存起點、路徑、終點狀態、射線和文字紀錄，因此前端知道「結果」，卻不一定知道事件屬於哪個階段、彼此有何關係。

這個缺口可以透過新增結構化事件記錄改善，不必先改寫戰鬥規則。真正需要另外評估的底層問題是時間模型：目前 2.5 秒同時被用作伺服器步進間隔、畫面播放時長及部分遊戲時間換算，但行動點設計源自較早的 10 秒 tick。

## 2. 現有引擎已經處理的順序

`engine/tactical/sim.py` 的 `Battle.step()` 目前大致依下列順序執行：

1. 戰術 tick 增加，重設本步移動和射擊旗標（`step()` 開頭）。
2. 非移動單位先面向威脅（`face_threats()`），套用姿勢與監視方向。
3. 建立移動、拖行、撤離、警戒和行動點預算（`move_budget()`）。
4. 以多輪微步驟處理移動與位置衝突（`step()` 的 `while movers` 迴圈）。
5. 每輪移動後更新偵測（`detect("move<n>")`）。
6. 移動中觸發警戒射擊；已架槍者優先於未架槍者（同一迴圈內 `braced_pass`）。
7. 移動結束後重新面向威脅和更新偵測（`detect("post_move")`）。
8. 以移動後快照計算一般射擊、投擲、近戰、急救和物資交接（「快照 2」段落），最後 `_update_braces()`。
9. 射擊以批次套用損傷和壓制；同一批次內維持同時結算語意（`Battle.apply()`）。開火者在 `apply()` 中經 `reveal_fire()` 暴露大概位置。

> 註：已改用函式名稱引用（行號會隨修改移動）。本文件撰寫後，引擎新增了開火暴露（`reveal_fire`）、架槍兩步（`BRACE_STEPS`）、警戒射擊限制（`OW_MIN_VIS`、每個移動目標一步一發）與連續地圖（`engine/zone.py`）。結構化事件以連續地圖為準。

因此畫面需要的主要事件順序已存在於程式流程中。缺少的是穩定、結構化且經迷霧過濾的輸出。

## 3. 現有回放資料

`engine/replay.py` 的 `FrameRecorder` 目前保存：

- 單位起點、逐格路徑和終點。
- 姿勢、朝向、壓制、架槍、倒地、死亡、撤出等終點狀態。
- 射擊起點、終點、碰撞類型和命中單位。
- 爆炸、煙霧和支援。
- 戰鬥 log 轉成的文字事件。
- 各方在該影格的 spotted 與 last-known 情報。

`for_viewer()` 再依玩家情報過濾敵人、射線和文字事件。這套權限邊界必須保留。

## 4. 畫面缺少的資料

| 缺口 | 畫面影響 | 建議記錄 |
|---|---|---|
| 事件在 step 內的階段 | 無法分辨移動中警戒射擊與移動後交火 | `phase`、`substep`、`sequence` |
| 射擊性質 | 無法清楚表現警戒、瞄準或壓制射擊 | `fire_mode`、`overwatch` |
| 壓制來源 | 只能看到單位遭壓制，不知道主要火力方向 | `actor`、`target`、`amount` 或強度級別 |
| 命中、受傷與倒地關聯 | 射線和倒地可能看似無關 | 共享 `action_id` 或因果 ID |
| 急救與拖行配對 | 只能看到位置或終點狀態 | `actor`、`target`、開始／完成／中斷 |
| 投擲過程 | 只看到爆炸或效果落點 | 投擲者、物件、出手點、落點、效果時間 |
| 行動受阻原因 | 玩家只看到單位停止 | 掩體不足、遭釘死、路線阻擋、友軍擋線等規則理由 |
| 同時結算語意 | 錯開動畫後可能誤導成先手擊殺 | `resolution_group` 或 `simultaneous` |

「瞄準」「裝填」「舉槍」不一定都是模擬狀態。若只是讓既有結果更自然地播放，應明確標成表演動作，不可反向解讀為戰鬥規則。

## 5. 結構化事件草案

以下只定義方向，不是最終協定：

```json
{
  "sequence": 1842,
  "phase": "movement_overwatch",
  "substep": 3,
  "type": "shot",
  "actor": "alpha-2",
  "target": "enemy-1",
  "action_id": "t51-ow3-alpha-2-0",
  "resolution_group": "t51-ow3-braced",
  "simultaneous": true,
  "data": {
    "fire_mode": "aimed",
    "from": [42.0, 18.0],
    "to": [53.2, 15.8],
    "impact": "cover"
  }
}
```

基本原則：

- `sequence` 在同一影格內穩定排序。
- `phase` 與 `substep` 對應模擬階段，不必使用毫秒時間。
- `action_id` 串連射擊、命中、壓制、受傷和倒地。
- `resolution_group` 表示同一批同時結算，避免動畫順序暗示不存在的先後因果。
- `data` 只包含畫面需要且玩家有權知道的資料。
- 新事件欄位和既有 frame 欄位並存，讓舊前端仍可運作。

## 6. 迷霧與資料安全

結構化事件不能直接把伺服器真相送到前端。所有事件必須先經過與 `for_viewer()` 同等的玩家視圖過濾。

最低要求：

- 看不見的敵人不能因角色 ID、事件類型、音效或彈道起點而洩漏精確位置。
- 未知射手只允許呈現玩家可知的彈著、聲音方向或部分射線。
- 最後已知位置不能持續播放該敵人的真實動作。
- 玩家不知道的命中、急救、死亡和投降事件不得傳送。
- 音效精度必須符合引擎提供的情報精度。
- GM 和一般玩家使用不同的過濾結果，而不是前端自行隱藏完整資料。

## 7. 2.5 秒時間模型

### 7.1 現況

較早的戰鬥設計在 `docs/combat.md` 將一個戰術 tick 定義為 10 秒、每人 2 AP；行軍時 6 AP 約為 12 m／10 秒。網頁版後續將作戰 tick 設為 5 秒，並在一個作戰 tick 內推進兩次戰術層，因此 `step_seconds` 為 2.5 秒。

目前部分介面時間採 `step_seconds` 換算，例如最後已知位置年齡和支援抵達時間；但 `move_budget()` 的接敵行動點仍為 2 AP。這表示「一步在真實時間播放多久」和「一步代表多少遊戲內行動量」尚未完全分離。

### 7.2 必須拆開的參數

| 參數 | 定義 | 影響範圍 |
|---|---|---|
| 模擬粒度 | 一次規劃與結算允許多少行動量 | AI 反應、警戒、同時結算、平衡、CPU |
| 遊戲時間尺度 | 一個模擬 step 在世界中代表幾秒 | 行軍速度、效果持續、情報年齡、支援 ETA |
| 網路推送間隔 | server 多久產生一次新 frame | 延遲、payload、server 負載 |
| 畫面播放時長 | 前端花多久播完一個 frame | 可讀性、張力、是否落後即時狀態 |

這四者可以相關，但不應只靠同一個 `step_seconds` 隱含決定。

### 7.3 2.5 秒可能太長的症狀

- 單位發現威脅後看似停頓才反應。
- 一個 step 內包含太多移動、射擊和傷亡，畫面難以建立因果。
- 玩家下令後，要等待下一次規劃才看見回應。
- 前端為了播完所有事件而持續落後伺服器。

### 7.4 2.5 秒可能太短的症狀

- 玩家還沒理解上一輪戰況，新事件已經抵達。
- AI 過度頻繁重新規劃，造成抖動或缺乏承諾感。
- 網路、序列化和路徑搜尋成本不成比例增加。
- 需要重設所有以 tick 計算的壓制、支援、整補和自主行為。

### 7.5 評估選項

**選項 A：維持目前模擬粒度，先改善事件記錄和播放。**

優點是風險最低，不破壞既有批次平衡。平靜移動可以壓縮播放，交火時依事件密度分配時間。這應是第一個驗證項目，但不是預先認定的最終答案。

**選項 B：縮小模擬粒度。**

例如降低每步可用 AP 或增加戰術步頻率。反應可能更細緻，但 AI、效果持續時間、移動速度和所有批次平衡都必須重新驗證。

**選項 C：保留模擬粒度，重新定義世界時間。**

明確規定一個 step 代表的遊戲秒數，修正行軍、情報年齡、支援 ETA 和效果持續時間，讓數據彼此一致。此方案改善語意，但不會自行改善一步內事件太多的問題。

### 7.6 評估方法

不先猜測 2.5 秒是太長或太短。完成結構化事件記錄後，以固定遭遇測試：

- 首次看見敵人到轉向、射擊或隱蔽的體感延遲。
- 一個 frame 平均及尖峰事件數。
- 玩家是否能辨識警戒射擊、一般射擊和傷亡原因。
- 播放佇列落後伺服器的時間。
- 玩家能否在下一次重大變化前完成判讀與下令。
- 不同模擬粒度下的勝率、傷亡、耗彈、交火時間和 AI 行為。
- 40、100、200 個活動單位時的 step 執行時間。

只有在事件播放改善後仍明顯出現反應或同時結算問題，才調整模擬粒度。

## 8. 效能判斷

既有文件記錄 25×25 地圖的單 tick 曾由約 307 ms 優化到約 11 ms。連續地圖（125×125）約 40 人時，每作戰 tick 平均約 0.14～0.2 秒、最慢約 0.6 秒（`scripts/zone_bench.py`）；Phase 0 基線見 `docs/web/baseline.md`。以目前數十個活動個體、每 2.5 秒一步的目標而言，尚無證據顯示 Python 戰術計算追不上畫面。

未來應分開量測：

- `Battle.step()` 與 TacticalAI 規劃時間。
- 玩家視圖與事件過濾時間。
- JSON 序列化時間和 payload 大小。
- WebSocket 推送延遲。
- PixiJS update、render 和垃圾回收時間。

若 renderer 掉幀，不代表 simulation 太慢；若 server step 超時，換 renderer 也不會改善。

## 9. 建議實施順序

1. 建立一場固定種子或固定 replay 的代表性遭遇。
2. 定義最小事件種類與同時結算語意。
3. 在模擬發生處記錄事件，不從文字 log 反向解析。
4. 讓 `FrameRecorder` 保存結構化事件，保留既有欄位。
5. 在 server 端建立玩家事件過濾。
6. 先用回放播放器驗證事件順序和可讀性。
7. 接上即時戰鬥，量測播放佇列是否累積。
8. 最後才決定是否調整 2.5 秒及 AP。

## 10. 驗收條件

- 新增事件記錄前後，固定種子的戰鬥結果完全一致。
- 現有離線、戰術與 Web 測試維持通過。
- 一般玩家 payload 不含不可見敵人的 ID 或精確位置。
- 同時結算事件在 replay 中保持同一 resolution group。
- 回放和即時模式使用相同事件語意。
- 舊前端可在忽略新欄位的情況下繼續運作。
- 在實測資料出現前，不把 2.5 秒定性為過長或過短。
